# 本番モード（bisync）と Raspberry Pi の検証計画

[migration-plan.md](migration-plan.md) の各フェーズで行う検証を、シナリオと合格基準にまとめる。
結果は、[test-log.md](../03_progress/test-log.md) に記録する。障害は [incident-log.md](../03_progress/incident-log.md) に記録する。

## 1. 検証の進め方

1. **検証用のサブフォルダ**（例: `protondrive:naspi-test`）で、A 群・B 群を行う。本番データには触れない。
2. 合格したら、`RCLONE_REMOTE=protondrive:` に切り替え、C 群以降を行う。
3. 検証中は、**開発環境の rclone マウントを止める**（同じクラウドを 2 か所から書き換えない）。
4. 破壊的な操作（削除の上限、異常終了）は、必ずサブフォルダで行う。

実行コマンドの目安（コンテナ名は `naspi_rclone`、同期は Bot の `/sync` または次のコマンド）:

```
docker exec naspi_rclone sh /config/rclone/sync.sh once
```

同期の結果は、`/log`、`history/sync.tsv`、`history/sync.last.log` で確認する。

## 2. 検証項目

優先は、**必須**（これがなければ本番にしない）、**推奨**、**任意**。

### A 群: bisync の基本動作（検証用サブフォルダ）

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| A1 | 初回同期 | ローカルを空にして、クラウドに数十ファイル（フォルダ、日本語名、空フォルダ、大きめのファイルを含む）を置いて同期 | 初回は `--resync` で実行される。ローカルにクラウドの全体が入る。**削除は行われない**。`rclone check` で差分なし | 必須 |
| A2 | ローカルでの追加 → クラウド | ローカルにファイルを追加して同期 | クラウドに反映される | 必須 |
| A3 | クラウドでの追加 → ローカル | クラウド（Web または別の機器）で追加して同期 | ローカルに反映される | 必須 |
| A4 | 片側だけの更新 | 一方で内容を変更して同期 | 反対側に反映される | 必須 |
| A5 | **競合**（両側で同じファイルを変更） | 両側を別の内容に変更し、更新時刻に差をつけて同期 | **新しいほうが勝つ**。負けたほうは `.conflict1` のような名前で残る。どちらも失われない | 必須 |
| A6 | 削除（ローカル → クラウド） | ローカルで削除して同期 | クラウドからも消える | 必須 |
| A7 | 削除（クラウド → ローカル） | クラウドで削除して同期 | ローカルからも消える | 必須 |
| A8 | 名前の変更・移動 | ファイルとフォルダの名前を変えて同期 | 反対側に反映される。重複が残らない | 推奨 |
| A9 | **削除の上限（`--max-delete 50`）** | 全体の 50% を超えるファイルを、片側で削除して同期 | `Safety abort: too many deletes` で停止する。**どちらも変更されない**。失敗として記録され、通知が届く。`--force` で実行すると反映される | 必須 |
| A10 | クラウド側の削除でも、上限が働く | A9 を、クラウド側の削除で行う | 同じく停止する（ローカルでの確認は済み。クラウド側は未確認） | 必須 |
| A11 | 日本語・記号・長いパス・大文字小文字 | Proton Drive の制約を含め、名前の扱いを確認 | 欠落・文字化けがない | 推奨 |
| A12 | 大きなファイル（数百 MB） | 同期にかかる時間と成否 | 中断せず完了する。時間を記録する | 推奨 |
| A13 | 同期中に更新されるファイル | 同期の実行中に、ファイルを更新 | 次回の同期で整合する。壊れたファイルが残らない | 推奨 |

### B 群: 異常系と自己回復（検証用サブフォルダ）

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| B1 | **認証切れ** | `rclone.conf` の認証情報を（コピー上で）無効にして起動 | `history/sync.state` ができる。**ログインを再試行しない**。CLOUD に「再認証が必要」の通知が届く。認証し直すと、自動で再開し、回復の通知が届く | 必須 |
| B2 | 同期の途中でコンテナを停止 | 同期の実行中に `docker stop` | 次回の同期で復旧する（`--resilient`、`--recover`）。データが壊れない | 必須 |
| B3 | 致命的エラー後の扱い | `*.lst-err` がある状態 | 自動では復旧せず、手動の `--resync` を促すメッセージが出る | 推奨 |
| B4 | ネットワークの切断 | 同期の前にネットワークを切る | 失敗として記録・通知される。復旧後に、自動で再開する | 必須 |
| B5 | 再起動後の復帰 | Raspberry Pi を再起動 | 全コンテナが自動で起動する。同期は、次の 00 分・30 分に実行される（起動直後には実行しない） | 必須 |
| B6 | 電源断 | 同期やバックアップの途中で電源を切る | 起動後に、古い印のファイル（`sync.lock`）が残っても、動作に支障がない。データが壊れない | 推奨 |
| B7 | レート制限 | 連続して認証に失敗 | 再試行を止めている（B1）ため、`Too many recent logins` を招かない | 推奨 |
| B8 | 時計のずれ | 時刻を意図的にずらして競合を作る | 競合の勝敗が、更新時刻に従う。NTP が効いている | 推奨 |

### C 群: 本番データ全体への切り替え

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| C1 | 容量の確認 | `rclone size protondrive:` と、SSD の空き容量 | ローカルコピーが SSD に収まる（余裕を持つ） | 必須 |
| C2 | 初回の全体同期 | ローカルを空にして、`RCLONE_REMOTE=protondrive:` で同期 | 完了する。所要時間・通信量を記録。`rclone check` で差分なし。**削除は行われない** | 必須 |
| C3 | 通常運用の同期 | 30 分ごとの自動同期を 24 時間 | すべて成功する。所要時間が、30 分の間隔に収まる（排他・見送りが頻発しない） | 必須 |
| C4 | 同期の所要時間 | 変更がないときと、少数のファイルを変更したときの時間 | 変更がなければ、短時間で終わる | 推奨 |

### D 群: バックアップと復元（本番の `/data`）

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| D1 | HDD での初期化 | HDD に `restic init`（exFAT の場合は特に） | 初期化でき、バックアップと復元ができる。**exFAT で問題があれば、ext4 を検討する**（D4） | 必須 |
| D2 | 初回のバックアップ（全体） | `/backup` を実行 | 完了する。所要時間・容量を記録 | 必須 |
| D3 | 固定時刻の自動実行 | 03:15 の自動実行を翌朝に確認 | 履歴に記録される。日次レポートに出る | 必須 |
| D4 | **同期との排他** | バックアップ中に同期の時刻が来る／同期中にバックアップを開始 | 同期は見送られる（終了コード 5）、バックアップは待つ。互いに壊れない | 必須 |
| D5 | 復元テスト（本番の `/data`） | `restore-test.sh`（サンプル、網羅性） | 成功する。網羅性が 99% 以上 | 必須 |
| D6 | 世代管理 | 日をまたいで、日次 7・週次 2 の世代になるか | 古い世代が削除される。`partial` が残らない | 推奨（日数が必要） |
| D7 | 別マシンでの復旧 | HDD とパスワードだけで、別のマシンから復元 | 復元できる | 必須 |
| D8 | 古い世代の復元 | 数日後の世代から復元 | 復元できる | 推奨 |
| D9 | 全データの検査 | `restic check --read-data` | エラーなし。所要時間を記録 | 推奨 |
| D10 | 不完全なスナップショット（本番） | バックアップ中に、読めないファイルを作る | 終了コード 3 で `partial` が付く。次の完全なバックアップで削除される（開発環境では確認済み） | 任意 |
| D11 | HDD の未接続 | HDD を外して起動・バックアップ | 失敗として通知される。別の場所に、誤ってリポジトリを作らない | 必須 |

### E 群: Samba と iPad

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| E1 | PC からの読み書き | Cloud-Sync と Local-NAS に接続 | 読み書きできる。所有者が UID 1000 | 必須 |
| E2 | **iPad からの読み書き** | ファイルアプリで接続。PDF を開いて書き込み、保存 | 保存できる。同期でクラウドに反映される | 必須 |
| E3 | 同期中のアクセス | 同期中に、読み書き | 失敗やファイルの破損がない | 推奨 |
| E4 | 転送速度 | 大きなファイルの読み書き | 記録する。基準は 3 を参照 | 推奨 |
| E5 | Samba の認証 | 誤ったパスワード | 接続できない | 推奨 |

### F 群: Discord Bot（本番）

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| F1 | 起動とパネル | 本番のチャンネルで起動 | **開発用ボタンが出ない**。チャンネルの警告がない | 必須 |
| F2 | `/sync`（本番） | ボタンから実行 | bisync が 1 回実行され、結果が CLOUD に出る | 必須 |
| F3 | `/backup`、`/log`、`/status` | それぞれ実行 | 期待どおり。`/status` に実行時刻と次回の予定が出る | 必須 |
| F4 | 通知（本番） | 失敗・回復・認証切れ・日次レポート | CLOUD と BACKUP に、状態が変わったときだけ届く。8:00 に日次レポートが届く | 必須 |
| F5 | 二重応答 | 開発用と本番用の Bot が同時に動く場合 | 同じ操作に、2 つが応答しない（D2 の決定が反映されている） | 必須 |
| F6 | スラッシュコマンドの登録（本番） | `deployCommands.js` | 本番のコマンドだけが登録される | 必須 |

### G 群: 性能と安定性

| No. | シナリオ | 手順の要点 | 合格基準 | 優先 |
| - | - | - | - | - |
| G1 | 負荷（同期、バックアップ、SMB 転送） | CPU 使用率、メモリ、CPU 温度を `/status` と `top` で記録 | 下の基準を満たす | 必須 |
| G2 | **1 週間の連続稼働** | 全機能を、本番の構成で 7 日間 | 重大な障害がない。失敗回数・遅延・例外を記録 | 必須 |
| G3 | ログの増加 | 1 週間後の、ログとディスクの使用量 | ログのローテーションが働く。SSD の空きが減り続けない | 推奨 |
| G4 | 再起動の繰り返し | 数回の再起動 | 毎回、自動で復帰する | 推奨 |

## 3. 合格基準（性能）

目安であり、実測して見直す。基準に満たない場合は、Raspberry Pi 5 への変更を検討する（[migration-plan.md](migration-plan.md) の D5）。

| 項目 | 基準（案） |
| - | - |
| CPU 温度 | 通常時 70℃ 未満、高負荷でも 80℃ 未満（冷却を含めて確認） |
| メモリ | 4GB のうち、使用が 80% 未満。スワップが増え続けない |
| 同期の所要時間 | 変更が少ないとき、1 回が 30 分の間隔より十分に短い |
| バックアップの所要時間 | 03:15 から開始して、同期の時刻（00 分・30 分）を何度もまたがない |
| SMB の転送速度 | 記録して、実用上の問題がないか判断する（iPad での PDF の閲覧・保存が快適か） |
